RESPONSE_SCHEMA defines direction as DERIVED per-pass from comparing that pass's own our_estimate to market_price ("YES if our_estimate > market_price and edge is worth acting on"), so a 0.7-YES sample and a 0.5-PASS sample are answers to two different implicit questions -- averaging our_estimate across disagreeing directions would blend framings. Design: direction is decided by majority vote across the N per-ticker samples; a genuine tie (e.g. 2 YES/2 NO, or an even split with no literal PASS votes at all) breaks to PASS as the conservative default rather than coin-flipping a side -- this tie-break rule was a judgment call made without asking the user first, since it's easily reversible code, not a data/business decision. our_estimate is then the mean taken ONLY over the samples that agreed with the winning direction (a fallback to averaging over every sample handles the edge case where PASS wins via tie-break but zero samples literally said PASS, avoiding a divide-by-zero on an empty agreeing-pool). edge is recomputed fresh from that aggregate estimate vs market_price rather than trusting any single sample's self-reported edge. confidence/reasoning are taken from whichever agreeing sample's own our_estimate is closest to the aggregate mean (the most "representative" individual call) -- there's no principled way to average a HIGH/MED/LOW enum or a reasoning string. sources and sources_checked are unioned (deduped by url / by string) across every agreeing sample, since each pass is a genuinely independent research pass. A ticker missing from some passes (a parse hiccup, or Claude omitting it from one pass's JSON array) is aggregated over however many passes did include it, with n_samples on the result recording how many of the N actually agreed. rescore_single_market() (a separate, already-existing single-market path built for per-pick source attribution when publishing subscriber picks -- see GOAL_phase2-6_decisions.md Decision 1) was deliberately left untouched: the backlog item text named score_markets specifically, and rescore_single_market solves a structurally different problem this change doesn't touch. multi_sample_n added to config.example.json documented at its default (1, off) -- the live config.json was deliberately NOT changed to enable multi-sampling by default, since turning it on multiplies the CLI backend's (the default, config.llm.backend="cli") scoring-step wall-clock time by roughly Nx per scheduled run; the CLI backend has no per-token dollar cost (rides the Pro OAuth subscription, not metered billing), but the runtime and Pro-plan-usage multiplication is real and hadn't been weighed against any specific N before this session. 22 new tests in tests/test_scorer.py (12 on _aggregate_multi_sample directly: unanimous/majority/tie-to-PASS/PASS-majority/edge-recompute/representative-confidence-reasoning/sources-union/sources_checked-union/partial-ticker-coverage/_validate_scores compatibility; 4 on score_markets' multi_sample_n wiring: default-is-single-call, N-calls-backend-N-times for both CLI and API backends, N=1-explicit-matches-default, API token_info summed correctly across passes).
